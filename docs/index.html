The problem

Calling an LLM in a loop is the easy part.

A demo agent runs once, in a notebook, while someone watches. A service runs thousands of times, unattended, on machines that crash, against APIs that fail, with a bill at the end of the month. This project answers the questions a demo never has to.

What breaks in production
  • 💥A worker dies halfway through a 2-minute run. Is the job lost? Does it run twice?
  • 💸Step 5 of 6 fails. Do we pay for steps 1–4 again?
  • 📈An agent loops and burns tokens. Who notices, and when?
  • 🤷Is the system "fine"? By what definition?
  • 🔓Who can start research, see costs, or manage accounts?
How this project answers it
  • 🔒Leased jobs with heartbeats: dead workers' jobs are reclaimed, and each job has exactly one owner
  • 💾A versioned checkpoint after every iteration: resume where it failed
  • 🧮Per-run token budgets, per-call cost tracking, and a spend-rate alert
  • 🎯5 SLOs with error budgets, burn rates and alerts
  • 🛡️Sessions, 4 roles checked on every route, CSRF and brute-force protection
Architecture

Six services, one source of truth.

PostgreSQL is the queue, the event log, the checkpoint store and the metrics source. There's no Redis and no broker, so there's one thing to back up and one place where the truth lives. Workers scale out by running more of them.

Life of a request

From question to answer, one job at a time.

The HTTP request returns in milliseconds. The research runs in the background, and the browser follows it live.

Queue

POST /research stores the task and a PENDING job, then answers 202 Accepted. Nothing slow happens inside the request.

Claim

A worker takes the job with FOR UPDATE SKIP LOCKED, marks it RUNNING and takes a lease, which it renews on a heartbeat.

Research

The agent loops: the LLM picks searches, tools run them (with retries), and every step, token and cent is recorded. A checkpoint follows each iteration.

Stream

Each event lands in the job's event log. GET /events streams it to the browser over SSE and resumes with Last-Event-ID after a dropped connection.

Answer

The agent writes a summary from the evidence it gathered and says when the evidence is thin. The task moves to COMPLETED.

Engineering decisions

The interesting parts.

Each of these is a real problem I ran into while building it, what I chose, and why.

01 · Job queue

A crash-safe queue in PostgreSQL, without Redis or Celery

SKIP LOCKED lets any number of workers poll one table without ever getting the same job, and the job is in the same database as the task it belongs to, so there's no dual-write problem.

Each claim carries a lease, renewed on a heartbeat. When a worker dies, its lease expires and the job goes back on the queue. When a worker finds its lease taken over, it cancels its own run instead of spending tokens on work it no longer owns. On SIGTERM it finishes or hands back the current job, so deploys don't lose work.

app/jobs/worker.py · app/jobs/service.py · app/services/recovery_service.py
# Claim the next job: safe with any number of workers.
query = (
    select(ResearchJob)
    .where(ResearchJob.status == JobStatus.PENDING)
    .order_by(ResearchJob.created_at.asc(), ResearchJob.id.asc())
    .limit(1)
    .with_for_update(skip_locked=True)
)

# Heartbeat, every WORKER_HEARTBEAT_SECONDS:
renewed = await renew_job_lease(...)
if not renewed:
    # Recovered and possibly claimed by another worker:
    # stop working on it.
    current.lease_lost = True
    current.task.cancel()
02 · Checkpoint & resume

Never pay for the same LLM call twice

After every iteration the agent saves a versioned checkpoint: the conversation so far, tool results, and the token totals. POST /research/{id}/resume restarts a failed task from its last checkpoint, and its token and cost totals carry over, so budgets stay honest across attempts.

A checkpoint from an older layout is rejected clearly rather than half-read, which is what keeps resume safe across deploys.

  • Crash at step 5 → resume at step 5
  • Budget counts every attempt, not just the last one
  • Worker shutdown hands work back with its checkpoint
class AgentCheckpoint:
    iteration: int             # a resume starts at the next
    input_items: list          # the conversation so far
    tool_call_count: int
    executed_tool_calls: int   # search limit carries over
    input_tokens: int
    output_tokens: int
    total_tokens: int          # token budget carries over
    estimated_cost: float | None
    version: int = CHECKPOINT_VERSION

# After each finished iteration:
await self.on_checkpoint(checkpoint)

# Later, a resume carries on from there:
await agent.run(question, checkpoint=saved)
03 · Cost control

Cost is a metric, not a surprise

Every LLM call records input, cached-input and output tokens, priced against a per-model table. Each run has a token budget and stops before it overspends.

Cost is visible per run, per task and system-wide, and the HighLLMCostRate alert fires when spend accelerates, so a runaway loop is a page within minutes, not a line on next month's invoice.

app/llm/pricing.py · app/agents/research_agent.py

04 · Live updates

Streaming without hogging the database

The first version of GET /events held a pooled connection open for the whole stream: one connection per open browser tab, mid-transaction, for minutes. That's enough to exhaust the pool and block migrations.

Now each poll uses its own short-lived session, and a regression test asserts that exactly one session is open while streaming. The browser resumes from Last-Event-ID after a dropped connection, and a 401 stops the stream instead of retrying forever.

Security

Real accounts, real sessions, real roles.

I started with JWTs and replaced them with server-side sessions. The deciding factor was revocation: when an admin deactivates someone or a password changes, access should end immediately, not when a token happens to expire.

🍪

httpOnly session cookie

Page scripts can't read it. SameSite=Lax, and only its SHA-256 is stored, so a leaked database copy can't be used to sign in.

⛔

Instant revocation

Sign-out, a password change and deactivation end sessions everywhere. Expired sessions are swept automatically.

🧱

CSRF protection

Requests that change something are refused when they come from a foreign origin, on top of SameSite.

🐢

Brute-force throttling

Failed sign-ins are limited per username and per IP address, with 429 and Retry-After.

🔑

Argon2id + timing safety

Unknown usernames take as long as wrong passwords, so timing doesn't reveal which accounts exist.

👑

No lock-out

The system refuses to deactivate or demote the last active admin.

Role-based access, enforced on every route

viewer
  • See research & jobs
  • Read results
researcher
  • Everything a viewer can
  • + Start research
  • + Resume failed tasks
operator
  • Everything a researcher can
  • + Metrics & costs
  • + SLOs, workers
admin
  • Everything an operator can
  • + Manage users & roles

A test walks every route × every role and fails if a new endpoint forgets its permission check. The UI hides what a role can't do, but the server is what enforces it.
